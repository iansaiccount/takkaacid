# The pictures in this book

Every image here is a screenshot of the real panel, taken from a scratch session so nothing of the photographer's own
is in the book. This file records, per image, the state the app was in and the exact commands. Nothing is generated by
the build: the pictures are committed PNGs, and this note is what makes them replaceable when the panel changes.

## The session they came from

- **App:** the working tree at whichever commit last touched `rust/` — the same commit that carries this file — on
  2026-11-15, with `cargo build -p acid-app --bin takka-acid`. No hash is quoted on purpose: it would rot the moment the
  code moved, and `git log -1 -- rust/` answers it.
- **Scratch data directory:** `TAKKA_ACID_DATA_DIR=/tmp/takka-guide-46`, emptied before the first launch, so the session
  is a first run — the Slow Acid demo, named "New song", unsaved, pattern `A1`, 118 BPM. The theme round added a second
  device on `FESTIVAL CITRUS`, which is why the strip pictures show a teal cell beside a black one.
- **Display:** offscreen, `Xvfb :90 -screen 0 2000x1400x24`, with
  `DISPLAY=:90 WINIT_X11_SCALE_FACTOR=2 LIBGL_ALWAYS_SOFTWARE=1 WAYLAND_DISPLAY=`. The window is the design size in
  logical pixels (980 × 670) and renders at 1960 × 1340, so the silkscreen stays legible when a page scales it down.
- **Grab:** `import -window <id> NAME.png` — the whole window, which is 1960 × 1340. A crop is a second grab of the same
  window in the same state, never a cut-out of a finished image, so a picture and its crop cannot disagree:
  `import -window <id> -crop WxH+X+Y NAME.png`, in pixels of the 1960 × 1340 grab.
- **Pointer and keys:** `xdotool`, which is what changed from the last edition of this book. The old recipe had no pointer
  tool, so the cards that need a click were prose; they are pictures now.
  `xdotool mousemove X Y` and `xdotool click 1`, with X and Y **doubled** from the panel's logical coordinates —
  `xdotool key F1` for the keys. The button rects are in the layout (`ui/layout.rs`, `ui/strip.rs`, `ui/device_card.rs`);
  do not read them off a screenshot, because a key's painted label and its hit area are not always where the eye puts them
  (this round's first attempt clicked `SAVE` six times while believing it was clicking `SONGS`).
- **The two drum-machine pictures** (`drum-face.png`, `kit-browser.png`) were retaken on 2026-11-20, from a session of their own:
  `TAKKA_ACID_DATA_DIR=/tmp/takka-guide-51`, emptied first, on `Xvfb :88 -screen 0 2200x1500x24` (the screen must be at least
  the design size doubled — check `xdotool getdisplaygeometry` before trusting a grab), the same scale factor and software GL.
  The app was launched on a first run and then driven: `+` → `DRUMS` added `DRUMS 2`, which arrives on `808` (so the browser reads
  `NOW: 808 - READ ONLY`), then `BANKS` → `Hard Techno Acid` twice loaded that demo's drum bank into it (the session was unsaved,
  so the row asked first), and `F3` → the card's `KIT` row opened the browser, which is where `kit-browser.png` comes from. No
  device was saved, so that picture shows a first run's rack with one extra machine on it.
- **The keys-and-tooltips round's two pictures** (`drum-face.png`, `help-card.png`) were retaken on 2026-11-20 from a session of
  their own: `TAKKA_ACID_DATA_DIR=/tmp/takka-guide-07`, emptied first, on `Xvfb :89 -screen 0 2200x1500x24` — `DISPLAY=:89
  xdotool getdisplaygeometry` said `2200 1500` before the app was launched, and `xdotool getwindowgeometry` then said
  `1960x1340`. `+` → `DRUMS` added `DRUMS 2`, which arrives on `808`; the notice was waited out and the pointer parked outside
  the window for `drum-face.png`, which is where the new underlines under `H` on `HIT` and `L`/`B`/`P` on the filter are visible
  (checked in a separate `-crop` grab before the picture was kept, never by cutting the finished image). `F1` put the card up
  for `help-card.png`, sent as `xdotool key --window <id> F1`: under Xvfb with no window manager the window never takes the
  keyboard focus, so a bare `xdotool key` is delivered nowhere and the grab comes out as the face again. The pointer was parked
  outside the window for that grab too, so no tip and no notice is in either picture. The grid is empty because a first run's
  drum machine has no bank; `drum-face.png`'s step column sits on step 1, which is also a beat-framed column, and the stroke is
  full height where the frame is per cell, so the two read apart.
- **`help-card.png` was retaken again on 2026-11-20**, in the arrows round: the card's two arrow lines changed, so the picture did.
  `TAKKA_ACID_DATA_DIR=/tmp/takka-guide-08`, emptied first, on `Xvfb :91 -screen 0 2200x1500x24` (`getdisplaygeometry` said
  `2200 1500` before the app was launched; `getwindowgeometry` said `1960x1340`). `F1` opened the card with the pointer first
  moved inside the window and the window focused — on that launch `xdotool key --window <id> F1` alone printed
  `XGetInputFocus returned the focused window of 1` and delivered nothing, so the first grab came out as the face again. The
  pointer was then parked outside the window and the card grabbed with no tip and no notice in it. The picture is over the
  first-run acid face, which is what a fresh session shows; the card is the same over either face.

## What is prose on purpose

One state still needs something the capture cannot do: a knob's hover tooltip. It is described in words in
[`06-the-knobs`](../06-the-knobs.md), not faked with a picture of some other state.

## Replacing them

Re-run the commands above against a clean `TAKKA_ACID_DATA_DIR`, update the commit and the date in this file, and check each
crop against the layout before trusting it — the band geometry is in `ui/layout.rs` and every band is a fraction of the
panel height. `bash check.sh` proves every image a page references still exists; it cannot prove any of them still matches
the panel.
